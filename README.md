# 慢节点识别与处理仿真系统

针对 64 卡同步数据并行训练的慢节点（straggler）问题，用纯 Python + NumPy 构建的
端到端仿真：一个**真实在训练的缩小模型**跑在**按真实情况模拟的集群**上，
中途按剧本注入多种慢因，系统自动识别、归因、决策、处理、复核，并量化收益。

## 快速开始

```bash
# 1. 跑 3000 步完整实验（约 3 分钟，输出三组对照 run）
python3 run_experiment.py

# 快速冒烟（缩小模型，约 1 分钟）
python3 run_experiment.py --steps 1500 --quick

# 2. 启动可视化页面
python3 serve.py            # 浏览器打开 http://127.0.0.1:8000

# 3. 跑测试
python3 tests/test_detector.py       # 检测器/控制器单测（10 个）
python3 tests/test_integration.py    # 端到端集成测试（6 个）
```

## 目录结构

```

  events.py      慢因事件注入：偶发/数据倾斜/持续慢/退化/温度周期/网卡/存储抖动
  model.py       纯 NumPy 小模型（Embedding→均值池化→MLP→分类），手写前向反向
  topology.py    集群拓扑、卡状态机、批大小拆分、拓扑感知 LR
  sampler.py     数据采样：长短互补的均衡分片 + 倾斜模式
  timing.py      单屏障同步计时模型 + AR(1) 卡级慢漂移噪声
  detector.py    MAD 鲁棒检测、分量归因、六类原因分类、置信度
  controller.py  决策：重分配/剔除/撤回/换卡加回、冷却与效果复核
  simulator.py   主引擎，串联上述模块

  reporting.py   导出页面所需 JSON

serve.py           零依赖静态服务器（gzip）
```

## 慢因分类与处理策略（题目要求 2、3）

| 类别 | 真实对应 | 识别证据 | 处理 |
|---|---|---|---|
| 偶发 `sporadic` | 一次性抖动 | 命中稀疏、无持续效率劣化 | **忍着**，只观察 |
| 数据驱动 `data_driven` | 分片数据特别长 | 工作量高但单位 token 效率正常 | **重分配**数据权重，无效则撤回 |
| 持续慢 `persistent_gpu` | 机器/硬件问题 | 效率持续差、多次强异常、无自愈回落 | 置信度≥0.9 才**剔除** |
| 退化 `degrading_gpu` | 硬件快坏了 | 效率单调爬升、峰值回落极小 | 剔除 |
| 温度周期 `thermal_cycle` | 温度降频 | 长窗出现慢-恢复循环、效率显著回落 | **不剔**，周期会自愈 |
| 机器级 `host_level` | 网卡被抢 | 同机多数卡共因、持续门槛 | 持续足够久才整台处理，否则观察 |
| 集群时间窗 `cluster_window` | 共享存储抖动 | ≥50% 卡同时异常 | 谁也不剔 |

### 防止误判（题目要求 5）的多层保护

1. **鲁棒统计**：同侪基线全部用中位数 + MAD（中位数绝对偏差），单卡离群不拉偏基线；
2. **工作量/效率解耦**：先区分「活多」还是「卡慢」，数据问题绝不走剔除；
3. **自愈证据**：退化/持续慢判决要求长窗口效率峰值回落 < 12%，
   温度/网卡等会自愈的事件回落通常 >25%，从根上区分；
4. **多重确认**：连续多个判决点成立 + 置信度门槛 0.9 + 最小严重度（慢 30%）；
5. **数量保护**：最多剔除 1/4 卡，超出拒绝；
6. **撤回复核**：剔除后观察窗内若「命中序列像周期」且「客观指标无改善」则加回。

## 剔除后的批大小与学习率（题目要求 4）

- **global 策略（默认）**：全局批大小恒为 512，剩余卡按权重分摊（本地批取整保证总和不变），
  梯度按样本数加权 all-reduce，数学上等价于全量批；LR 不变，仅做 15 步线性再热身。
- **local 策略**（`--policy local`）：每卡批大小固定，剔除后全局批缩小，
  LR 按线性缩放规则（Goyal 等）同比缩小，再热身后保持。
- 维修/换卡完成的卡通过 rejoin 队列重新加入，清空检测历史重新观察。

## 五项评估指标（题目要求 6 + 验收口径）

`output/experiment_report.json` 与页面顶部 KPI：

1. **等待占比降幅**：按满配卡数归一化，full 相对 observe 的相对下降；
2. **同损失总时间**：以 clean 组最终损失为目标，比较三组达到它的墙钟时间；
3. **误剔除数**：剔除动作对照 ground-truth，剔除时不处于真坏状态即记误剔；
4. **真坏卡发现时延**：事件注入步到第一次正确剔除的步数与墙钟；
5. **损失衔接**：每次剔除/加回前后 10 步窗口的损失相对差。

## 仿真保真度

- **模型真在算**：每张卡每步对自己的本地批做完整前向/反向（含 softmax、ReLU、
  embedding 散射梯度、动量 SGD、梯度裁剪），不是用随机数假装训练；
- **单屏障计时**：每步只有一个 all-reduce 同步点，墙钟取最慢卡，
  等待占比 = 全卡等待总和 / 忙碌总和；
- **噪声两层**：卡间固定能力差（±1.5%）为主，叠加 AR(1) 慢漂移和小白噪声，
  健康集群等待占比标定在 ~15%，与题目「近两成」吻合；
- **三 run 同种子**：full/observe/clean 除干预外随机流完全对齐，差异只来自处理动作。

## 一次完整实验的典型结果

```
误剔除 0 张，正确剔除 3 张（持续慢×2 + 退化×1），global / local 两种批策略均零误剔
真坏卡发现延迟：持续慢 ~130 步、退化 ~155 步
  （延迟是「零误剔」的有意代价：异常必须持续超过温度慢相位、确认不会自愈才动手）
温度卡、网卡机器、存储抖动全部正确保护，未误剔
墙钟节省 ~20%，归一化等待占比下降 ~49%
剔除/加回前后损失相对差 < 0.6%，训练曲线平滑衔接
```

## 设计权衡：发现速度 vs 误判代价

题目明确「把好卡剔掉也是损失，有把握才动手」。本系统把天平放在**低误判**一侧：

- 硬件类剔除要求异常持续 ≥130（持续慢）/180（退化）步，超过温度周期的慢相位（120 步），
  确保见过一次「可能的恢复」仍不恢复，才认定是真故障；
- 配合长窗口效率峰值回落 <12% 的单调恶化证据，周期事件（回落 >25%）无法通过；
- 代价是真坏卡的发现延迟在百步量级，但换来 0 误剔和自动撤回安全网。
  若实际场景更看重发现速度，可调小 `config.py` 的 `min_persistent_age`/
  `min_anomaly_age`，但需同步评估误剔风险。
